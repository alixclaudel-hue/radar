# Diagnostic ai_query — 23/09/2026

Lot : `observations/ai_query/2026-09-23T220000Z/` (10 échecs, sha `2a1f962`)

## Finding 1 : les reçus d'erreur ne conservent pas la cause de l'échec

- **Cause racine** : `write_receipt()` (scripts/ai_query.py:476) écrit
  `status="error"` mais n'inclut jamais le type ni le message d'erreur. Les trois
  sites d'appel en erreur (l. 586, 601, 613) passent tous `**meta` — qui contient
  `elapsed_ms`, `tier`, `prompt_chars`, `model`, `fallbacks` — mais aucun ne
  transmet le message d'exception ni le code HTTP. L'erreur part sur stderr
  (l. 585, 600, 609), qui est éphémère.
- **Preuve verbatim** : dans le lot, les 10 échecs ont `"payloads": []` et
  `"reason"` reconstituée PAR L'OBSERVATEUR à partir du contexte (elapsed, tier),
  pas par le script lui-même. Impossible de distinguer un 401 auth d'un 429 quota
  d'un timeout réseau à partir du seul reçu.
- **Correctif proposé** : ajouter deux champs optionnels au reçu d'erreur :
  `error_type` (slug court : `"cascade_exhausted"`, `"http_401"`, `"http_429"`,
  `"empty_response"`, `"syntax_error"`, `"timeout"`, `"network"`) et
  `error_detail` (message court, jamais de secret). Les trois sites `write_receipt`
  en erreur les transmettent via `**meta`.
- **Cas de banc qui le prouverait** : appel mocké qui échoue en 429 cascade
  épuisée → vérifier que le reçu écrit dans le fichier contient `error_type` et
  `error_detail`. Aujourd'hui le banc ne vérifie pas le contenu des reçus —
  le cas échouera avant correctif car ces champs n'existent pas.
- **Confiance** : certain

## Finding 2 : cascade épuisée sans distinction entre erreur récupérable et quota global

- **Cause racine** : quand tous les modèles d'un tier échouent en 429,
  `query_with_fallback` (l. 431-434) lève un `RuntimeError` générique avec le
  message de la DERNIÈRE erreur. L'appelant (l. 584-588) le traite comme
  n'importe quelle exception : stderr + reçu `error` sans détail. Deux cas
  dans le lot (fallbacks=5, 51s chacun) montrent que la cascade a parcouru les
  5 modèles pour rien — 51 secondes perdues.
- **Preuve verbatim** : `failures.jsonl` lignes 1-2 :
  `"fallbacks": 5, "model": "gemini-3.5-flash-lite", "elapsed_ms": 51294` et
  `"elapsed_ms": 51270`. Les 5 modèles heavy épuisés simultanément.
- **Correctif proposé** : ce n'est pas un bug de logique — la cascade DOIT
  essayer tous les modèles, un 429 sur un modèle ne condamne pas les autres.
  Le correctif actionnable est dans la finding 1 : tracer `error_type:
  "cascade_exhausted"` dans le reçu pour que le prochain lot puisse les compter
  sans reconstruction manuelle.
- **Cas de banc** : celui de la finding 1 couvre ce cas (cascade épuisée →
  reçu avec `error_type`).
- **Confiance** : certain

## Finding 3 : `main()` ne transmet pas le type d'erreur au reçu

- **Cause racine** : dans `main()`, les trois chemins d'erreur écrivent un reçu
  identique. Le site l. 584-588 attrape une exception générique sans en extraire
  le type ; le site l. 599-601 (réponse vide) n'ajoute pas `error_type:
  "empty_response"` ; le site l. 607-613 (syntax error) n'ajoute pas
  `error_type: "syntax_error"`. C'est la même finding que la 1, vue depuis
  l'appelant plutôt que depuis `write_receipt` — le correctif est unique.
- **Preuve verbatim** : `scripts/ai_query.py:586` :
  `write_receipt(args.mode, "error", elapsed_ms=..., **meta)` — aucun champ
  d'erreur dans `meta` à ce point.
- **Correctif proposé** : enrichir `meta` avec `error_type` et `error_detail`
  AVANT chaque `write_receipt("error")`. Trois sites, trois types :
  - l. 586 : `meta["error_type"] = "cascade_exhausted"` si `RuntimeError` et
    "cascade" dans le message, sinon `"api_error"` ; `meta["error_detail"]` =
    message tronqué à 200 chars.
  - l. 601 : `meta["error_type"] = "empty_response"`.
  - l. 613 : `meta["error_type"] = "syntax_error"` ;
    `meta["error_detail"] = str(syn_err)[:200]`.
- **Cas de banc** : même cas que finding 1 — un test par chemin d'erreur
  vérifiant le contenu du reçu.
- **Confiance** : certain

## Findings écartées

- **Échecs auth/connexion locaux (5 cas)** : causés par le problème ADC OAuth
  documenté au pt 44 de CLAUDE.md, corrigé par le gateway. C'est un problème
  d'environnement (clé API absente ou invalide), pas un bug du script. Hors
  périmètre `touchable`.

- **Timeouts (2 cas, 60-65s)** : temps de réponse de l'API Google, pas un bug
  du script. Le paramètre `timeout=60` dans `query_with_fallback` est déjà le
  bon réglage — le réduire augmenterait les faux timeouts, le rallonger
  retarderait la détection d'un serveur muet. Hors périmètre.

- **Erreurs ancien format (27 reçus remote sans tier/elapsed)** : précèdent la
  PR #199 qui a enrichi les reçus. Rien à corriger — les nouveaux reçus ont les
  champs. La finding 1 (ajouter `error_type`) couvre exactement ce qui leur
  manquait encore.
